# 수정계획: gnfsd 재시작 뒤 첫 옛-핸들 요청이 서버를 몇 시간 멈추는 문제

2026-11-18 에 호스트 PC 를 재부팅하고 gnfsd 를 다시 띄운 뒤, OPENSTEP 실기의 `/ndrv`(hard 마운트)가
`NFS server 192.0.2.10 not responding still trying` 에서 멈췄습니다. 그 원인을 계측과 소스 분석으로 밝히고
고치기 위한 계획입니다. codex 재검토를 한 번 거쳤습니다(§11).

> 상태: **단계 1·2 구현·시험·실기 검증 완료(2026-11-19), 단계 3(선택) 미착수.** 결과는 §12·§13 입니다.
> 원인은 §2·§3, 수정 방안은 §5, 시험은 §6 입니다. 수정 전 운영 절차는 §9 입니다.

## 1. 요약

- **문제**: gnfsd 는 다시 뜬 뒤 클라이언트가 예전 파일 핸들로 첫 요청을 보내면, 그 핸들을 찾으려고
  내보낸 트리를 한 번 훑어 경로를 표에 등록합니다(`handle.c` `rebuild`). 그런데 등록 함수 `intern()` 이
  표 전체를 처음부터 `strcmp` 로 비교하므로, 훑기 전체의 비용이 **항목 수의 제곱**입니다.
- **영향**: 서버는 한 줄기(단일 스레드)라 훑는 동안 다른 요청을 전혀 처리하지 못합니다. 지금의 내보낸 트리
  (`/path/to/NeXT_DRIVER`)는 400 만 항목이 넘어, 훑기가 **십수 시간에서 하루 넘게**
  걸릴 것으로 어림됩니다(§2). 클라이언트는 hard 마운트라 그동안 멈춰 있습니다.
- **README 의 전제와 다름**: README 는 "트리를 한 번 훑는 비용이 … 2861파일 트리에서 수십 ms 수준" 이라고
  적었습니다. 그 측정은 작은 트리에서 맞지만, 비용이 제곱으로 늘어 큰 트리에서는 맞지 않습니다.
- **범위**: 서버 쪽 `handle.c` 가 중심이고, 단계 2(§5.2)는 `nfs.c`·`rpc.c` 에도 닿습니다. 클라이언트·마운트 옵션·
  네트워크와 무관하고, READDIR `count` 수정(`PLAN_readdir_count_fix.md`)과도 별개입니다.

## 3. 근본 원인(코드)

- **`handle.c:89–126` `intern()`**: 같은 경로가 이미 있는지 `for (i = 0; i < g_count; i++) strcmp(…)` 로
  표 전체를 훑습니다. 새 경로 하나 등록에 O(n) 이고, 빈 표에 n 개를 넣으면 `strcmp` 가 n(n−1)/2 번입니다.
- **`handle.c:145–182` `rebuild_dir()`·`rebuild()`**: 트리의 항목마다 `intern()` 을 부릅니다. 그래서 전체가 O(n²) 이고,
  서버 수명마다 한 번 일어납니다(`g_rebuilt`).
  - "트리 전체" 라고 했지만 실제로는 깊이 32 초과, 1,024 B 넘는 경로, 열 수 없는 디렉터리는 건너뜁니다.
  - 심볼릭 링크 디렉터리는 따라가지 않고, 파일 시스템 경계(`-xdev`)는 넘습니다.
- **`handle.c:184–214` `fh_to_path()`**: 빠른 길(색인 + `hash_str` 검증)이 맞지 않으면, `(hi, lo)` 해시를 찾으려고
  표 전체를 다시 훑습니다(O(n)). 재구축 뒤에도 옛 핸들을 풀 때마다 O(n) 이고, 클라이언트가 쥔 옛 색인은 고쳐지지 않습니다.
- **`nfs.c`**: `fh_from_path()`(곧 `intern()`)를 부르는 곳은 MOUNT(223 행), LOOKUP(312 행), CREATE/MKDIR(`create_common`, 429 행)입니다.
  - 재구축 뒤에는 n 이 트리 전체 크기라 이 요청들도 느려집니다.
  - `fh_to_path()` 는 모든 핸들 인자에서 부릅니다(`arg_fh` 155 행, LINK·RENAME 의 둘째 핸들 494·533 행).
  - READDIR 은 `intern()` 을 부르지 않습니다. 다만 쪽마다 디렉터리를 처음부터 다시 읽는 따로의 O(d²) 이 있고(633–674 행),
    `PLAN_readdir_count_fix.md` §6 이 이를 "별개 성능 사안" 으로 남겨 두었습니다. 이 계획도 다루지 않습니다.
- **`rpc.c:264–289`**: `select()` → `recvfrom()` → `handle_one()` 의 한 줄기 고리입니다. 한 요청이 몇 시간 걸리면
  그동안 아무것도 받지 않습니다.

## 4. 영향 범위

- 큰 트리를 내보낸 채 gnfsd 를 다시 띄우면, 클라이언트가 옛 핸들을 쥐고 있는 한 같은 일이 되풀이됩니다.
  OPENSTEP 의 hard 마운트는 재전송을 멈추지 않으므로 클라이언트 쪽에서 피하기 어렵습니다.
- 재구축이 끝나도 표에 수백만 경로가 남아 메모리를 차지하고(§2), MOUNT·LOOKUP·CREATE 의 `intern()` 이 느려집니다(§3).
- 표는 덧붙이기만 합니다(REMOVE·RENAME 은 표를 고치지 않음). 그래서 한 번 본 경로는 서버 수명 동안 남습니다.
- README 의 "핸들은 서버 재시작을 넘긴다" 는 기능 자체는 옳습니다. 비용 모형만 틀렸습니다.

## 5. 수정 방안(단계별)

### 5.1 단계 1(필수): 표에 색인 둘을 더해 등록·찾기를 기대 O(1) 로

- **경로 → 번호 해시표**: `intern()` 의 직선 훑기를 바꿉니다.
  - 열린 주소법(open addressing)으로, 칸 수는 2 의 거듭제곱, 칸에는 표 번호(빈 칸은 −1)를 둡니다.
  - 칸을 고르는 해시는 무엇이든 됩니다. 같음 판정은 지금처럼 **절대 경로 문자열의 `strcmp`** 입니다.
  - 채움률 0.5 를 넘으면 두 배로 키우고 다시 넣습니다.
- **`(hi, lo)` → 번호 해시표**: `fh_to_path()` 느린 길의 직선 훑기를 바꿉니다. 열쇠는 이미 있는 `(hi, lo)` 입니다.
  - 같은 `(hi, lo)` 가 둘 이상이면 **가장 작은 번호(먼저 등록된 쪽)** 가 이기는 지금 동작을 지킵니다. 다시 넣을 때도 같습니다.
  - 균등 해시 모형의 생일 한계로는 400 만에서 약 4.3×10⁻⁷, 600 만에서 약 9.8×10⁻⁷ 입니다.
  - 다만 `hash64()` 는 두 32 비트 반쪽이 서로 기대는 꼴이라 균등성이 보장되지 않습니다. 또 내보낸 곳이 `/` 이면
    LOOKUP 은 `//name`, 재구축은 `/name` 을 만들어(`nfs.c:102–105`, `handle.c:160–165`) 같은 상대 경로가 두 열쇠로 들어갈 수 있습니다.
    `relpath()` 는 접두 비교에 경로 경계 검사가 없습니다. 이런 별칭은 시험(§6)에서 따로 봅니다.
- **선 위(wire) 호환**: 핸들 꼴(32 B: 번호, `GFSH`, `hash_str` 검증, `(hi, lo)`)과 **`hash_str()`·`hash64()` 알고리즘을 그대로** 둡니다.
  그래야 예전 gnfsd 가 낸 핸들이 그대로 통합니다.
- **포인터 안정성**: 문자열은 지금처럼 하나씩 따로 `malloc` 한 채 두고, 번호는 덧붙이기만 합니다.
  `nfs.c` 가 "stable interned pointer" 로 쓰기 때문입니다(LINK·RENAME 의 둘째 핸들, 487–508 행).
  포인터 배열·메타 배열만 `realloc` 합니다.
- **등록의 원자성**: 새 항목을 넣기 전에 배열과 두 색인의 용량을 먼저 모두 확보합니다. 할당이 실패하면 이전 상태 그대로 찾을 수 있게 둡니다.
  지금 코드는 세 배열을 하나씩 `realloc` 하므로, 이 차례를 그대로 늘리지 말고 실패 정책을 따로 정합니다.
- **폭**: `long`·`unsigned long` 은 LP64 에서 8 B 이고 선 위 칸은 32 비트입니다. 용량 두 배·곱셈 넘침을 막습니다.
  빠른 길의 `(long)idx < g_count`(193 행)는 ILP32 에서 큰 값이 음수가 될 수 있어, 부호 없는 비교로 바꿉니다.
- **덤으로 고칠 약점**(선택, 같은 단계): 빠른 길은 32 비트 `hash_str` 만으로 번호를 받아들이므로(192–196 행), 재시작 뒤
  그 검증이 우연히 맞으면 엉뚱한 경로로 풀릴 수 있습니다. 새 꼴 핸들(`(hi, lo)` 가 0 이 아님)이면 `(hi, lo)` 도 함께 맞대고,
  0 쌍(옛 꼴)은 지금처럼 다룹니다.
- **효과**: 등록·찾기가 표 크기에 대해 기대 O(1) 이 됩니다. 경로 길이만큼의 해시·비교 비용, 가끔의 O(n) 키우기, 탐침 몰림은 남습니다.
  - 재구축 시간은 디스크 훑기(`readdir`·`lstat`)와 위 비용으로 줄어듭니다.
  - 끝나지 않은 `find -xdev` 앞부분의 속도로 늘여 보면 400 만에 약 5 분, 600 만에 약 7.5 분입니다.
  - 이 수는 재구축이 파일 시스템 경계를 넘고 항목마다 할당·해시·`lstat` 을 하므로 더 길어질 수 있는 어림입니다.
  - 색인 메모리는 두 표를 합쳐 400 만에서 약 134 MB, 600 만에서 약 268 MB 가 더 듭니다(키울 때의 잠깐의 두 배는 뺌).
- **크기**: `handle.c` 안의 바꿈만으로 끝나고, `handle.h` 의 인터페이스는 그대로입니다.

### 5.2 단계 2(권장): 재구축 중에도 응답하기

단계 1 만으로도 서버는 몇 분 동안 멈춥니다. hard 마운트는 이를 견디지만, 그동안 새 마운트나 다른 클라이언트도 막힙니다.

- **나눠 훑기**: `rebuild_dir()` 의 재귀를 명시 스택(열린 `DIR *` 와 경로)으로 바꾸고, 한 번에 정해진 양만 훑습니다.
  - 한 조각은 항목 수(예: 2,000)와 시간(예: 50 ms, 단조 시계)으로 묶습니다.
  - 이 시간은 **목표**입니다. 파일 시스템 호출 하나나 색인 키우기 하나가 더 걸릴 수 있으니 따로 잽니다.
- **고리에 끼우기**: `rpc.c` 의 `select()` 에 시간 제한을 줍니다. 받을 요청이 없을 때만 훑으면, 요청이 끊이지 않을 때
  재구축이 영영 나아가지 않습니다(옛 핸들 재전송이 바로 그런 흐름입니다). 그래서 **바쁠 때도 요청 몇 개마다 한 조각씩**
  훑도록 공정 규칙을 둡니다.
- **재구축 상태**: 지금의 `g_rebuilt`(훑기 전에 1 이 됨)를 넷으로 나눕니다: 시작 안 함·도는 중·끝남·실패/덜 끝남.
  - 열기 실패·할당 실패로 덜 끝난 표를 "끝남" 으로 보지 않습니다. 다시 시도할지, 언제 STALE 로 끝낼지를 정합니다.
  - 끝나거나 그만둘 때 열어 둔 `DIR *` 를 모두 닫습니다.
- **풀 수 없는 요청은 답하지 않기**: 훑는 동안 빠른 길과 `(hi, lo)` 표로 풀리지 않는 옛 핸들 요청은 답하지 않고 버립니다.
  클라이언트(UDP, hard)가 재전송하므로, 훑기가 끝난 뒤 받은 재전송에 답합니다.
  - 이를 위해 `fh_to_path()` 의 결과를 "찾음 / 기다림 / 무효" 셋으로 나누고, "기다림" 을 `arg_fh()`(155 행)와 둘째 핸들 두 곳(494·533 행)에서
    처리기의 "버림" 반환으로 올려 보냅니다. 지금처럼 NULL 만 돌려주면 `arg_fh()` 가 STALE 로 답하고, 그 답이 DRC 에 들어갈 수 있습니다.
  - **버리기는 파일 시스템을 바꾸기 전에만** 합니다. CREATE/MKDIR·SETATTR 은 바꾼 뒤에도 `lstat`·핸들 할당을 하므로(273–289·401–435 행),
    그 뒤의 실패를 "버림" 으로 바꾸면 안 됩니다.
  - LINK·RENAME 은 두 핸들을 모두 먼저 풀어 본 뒤에 바꿉니다(487–509·527–547 행). 둘째가 "기다림" 이면 요청 전체를 버립니다.
  - **DRC**: `rpc.c:14–50` 에 256 칸·30 초의 응답 캐시가 있고, 처리기 앞에서 찾고 답을 보내기 전에 채웁니다(210–250 행).
    "버림" 판단은 이 캐시 찾기 **뒤에** 두어, 이미 끝난 요청의 답은 재전송에 그대로 다시 보내게 합니다.
    버린 시도는 실행되지 않았으므로 두 번 실행되지 않습니다.
    다만 DRC 는 칸 수·30 초·재시작에 한계가 있는 보호이지 정확히 한 번을 보장하지 않습니다. CREATE 의 `O_TRUNC`(419–423 행)처럼 되풀이가 해로운 요청이 있습니다.
  - NFSv2 에는 "잠시 뒤 다시" 오류(v3 의 JUKEBOX)가 없습니다. 기다리는 핸들에 STALE 로 답하면 클라이언트가 그 핸들을 버립니다.
    STALE 은 정말 무효인 핸들과, 재구축이 끝난 뒤에도 못 찾은 핸들에만 씁니다.
- **새 핸들 요청은 바로 처리**: MOUNT, 그리고 새 루트 핸들에서 시작한 LOOKUP 은 빠른 길로 풀리므로 훑는 동안에도 처리합니다.
- **트리 변경과의 겹침**: 나눠 훑는 동안 NFS 요청이 트리를 바꿀 수 있습니다. 열어 둔 디렉터리가 RENAME 되면, 그 아래 항목을 옛 경로로 등록하게 됩니다.
  스냅숏을 약속하지 않고, 못 찾은 옛 핸들은 재구축 뒤 STALE 이 되며, 새 경로는 LOOKUP 때 등록된다는 지금 동작을 문서로 밝힙니다.
- **진행 기록**: 훑기 시작·끝·몇 만 항목마다의 진행을 표준 오류에 한 줄씩 남깁니다. 이번처럼 "CPU 100 % 인데 무엇을
  하는지 모름" 을 막기 위함입니다.

### 5.3 단계 3(선택): 운영 스위치와 메모리

- **재구축 끄기 선택**(예: `-R`): 옛 핸들을 찾지 않고 바로 STALE 로 답합니다. 클라이언트를 다시 마운트할 생각이면
  가장 빠릅니다. 기본값은 지금처럼 재구축을 켭니다.
- **메모리 줄이기**(필요할 때만): 경로 전체 대신 "부모 번호 + 이름" 으로 두면 400 만 항목에서 경로 표가 수백 MB
  줄어듭니다. 경로는 찾을 때 이어 붙입니다. 바꾸는 범위가 커서, 단계 1·2 뒤에 메모리가 실제로 문제일 때만 합니다.
- **내보내기 범위 좁히기**(운영 쪽 대안): 실기가 쓰는 곳만 내보내면 n 자체가 줄어듭니다.
  지금 `/ndrv` 는 `NeXT_DRIVER` 전체이고, 그 아래 `openstep-kernel-remade/08_build/runs` 같은 큰 빌드 트리가 함께 들어 있습니다.

## 9. 지금 당장의 운영 절차(수정 전)

옛 핸들을 쥔 클라이언트가 있는 동안 gnfsd 를 다시 띄우면 같은 훑기가 다시 일어납니다. 그래서 차례가 중요합니다.

1. 매인 gnfsd 를 멈춥니다(호스트, 사용자).
2. gnfsd 가 꺼진 채로, 옛 핸들을 쥔 **모든** 클라이언트를 멈춥니다. 지금은 OPENSTEP 실기 하나뿐이며, 재부팅으로 옛 핸들을 모두 없앱니다.
   - hard 마운트 때문에 정상 종료가 멈출 수 있습니다. 그러면 강제 재시작합니다.
   - 이 실기는 부팅 때 `/ndrv` 를 저절로 마운트하지 않습니다(`NeXT_DRIVER/tools/nx-mount.sh` 로 손으로 함). 그래서 부팅이 끝난 뒤 gnfsd 를 띄워도 됩니다.
     저절로 마운트하는 클라이언트라면, 옛 커널이 내려간 뒤이자 새 마운트가 서버를 찾기 전에 gnfsd 를 띄웁니다.
3. gnfsd 를 같은 내보내기 경로(`…/NeXT_DRIVER`; MOUNT 는 문자열을 그대로 맞댐, `nfs.c:214–217`)로 띄웁니다.
4. 실기에서 새로 마운트(`tools/nx-mount.sh`)하고 gcdsd 를 시작합니다(`tools/nx-daemon.sh start`).
   - 새 마운트는 새 핸들을 받으므로 훑기가 일어나지 않습니다.

## 12. 단계 1 결과(2026-11-19)

**바꾼 것**(`handle.c` 만; `handle.h` 인터페이스·핸들 꼴·`hash_str`/`hash64` 그대로)
- §5.1 의 색인 둘 대신 **열린 주소 색인 하나**를 둡니다. 칸은 저장된 `(hi, lo)` 로 고르고(`slot_hash`, murmur3 fmix32),

## 13. 단계 2 결과(2026-11-19)

**바꾼 것**
- `handle.c`: 재귀 `rebuild_dir()` 를 명시 스택(열린 `DIR *` + 등록된 경로 포인터 + 깊이) 훑기로 바꿨습니다.
  `fh_walk_step()` 한 번이 2,000 항목 또는 50 ms(단조 시계, 64 항목마다 확인) 까지 갑니다. 차례는 옛 재귀와 같은 깊이 우선이고,
  깊이 33 항목까지 등록·34 는 아님, 너무 긴 경로·못 여는 디렉터리 건너뜀, 심볼릭 링크 안 따라감도 같습니다.
- 상태 넷(시작 안 함·도는 중·끝남·실패). 실패(루트를 못 엶, 할당 실패)는 "끝남" 이 아니라 따로 기록하고, 열린 `DIR *` 를 모두 닫고,
  표에 없는 옛 핸들은 STALE 로 답합니다(같은 이유로 또 실패할 것이라 다시 시도하지 않음).

- `rpc.c`: 일반 계층이 핸들을 모르도록 `rpc_set_background(pending, step)` 를 두었습니다. 도는 동안 `select()` 는 기다리지 않고,

- `nfs.c`: `arg_fh()` 가 0(풀림)·1(STALE 답)·−1(버림) 셋으로 돌려주고 `ARG_FH()` 가 처리기를 그에 맞게 끝냅니다(13 곳).
